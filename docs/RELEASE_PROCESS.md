# Release process

Version candidates v0.x.x; v1.0.0 reserved for professional launch. Confirm milestone scope, create dedicated branch, implement, run checks, open review PR, document actual results and limitations, obtain owner acceptance and owner-controlled merge. No automatic merge. Tag/release only with authorization. Publication requires separate explicit approval and manual production deployment, not merely merge. Public repo content is already public, regardless of Pages status. Review all files and assets before commit; never use secrets in logs or artifacts.

Build verification: npm ci on Node 24, npm run check, npm run build; browser, accessibility, unit and performance checks introduced at relevant milestones. No deployment workflow in PP-004A.

## PP-004E release protocol (production disabled)
The workflow .github/workflows/deploy.yml is manual only. Do not activate Pages or invoke publication before PP-007. config/release.json starts with publicationEnabled false, null approval reference and null version; machine validation rejects publication until an authorized launch PR changes it. The future launch PR must also update development-mode checks, remove development specimens and labels, update responsive tests for production, add approved content, configure indexing, and validate all launch criteria. Passing the gate is not proof of actual approval.
At authorized launch, owner reviews content, QA, exact main SHA and v1.0.0 (or approved later production version); verifies publishing source is GitHub Actions and github-pages environment protection restricts deployment to main. Configure permissions/review protections where supported by the account. Choose the approved main ref manually in Actions, supply exact SHA and confirmation phrase PUBLISH APPROVED PORTFOLIO. Workflow checks branch, SHA, confirmation, approved release reference/version, full CI gates and builds only dist, then uses an isolated Pages deployment job. No direct deploy from PRs. Actual Pages settings/environment protection and end-to-end deployment have not been verified or activated. Do not treat noindex as access control.
After authorized deployment verify site, mobile, links, TLS, metadata and actual URL; roll back via reviewed revert/rebuild and separate authorized dispatch. No automatic rollback or domain purchases.

## PP-007B.1 prepared production artifact path (no activation)
As of v0.13.0 candidate, the normal build post-step copies font licenses and runs `scripts/prepare-static-artifacts.mjs`. While `config/release.json.publicationEnabled=false`, it performs **no** release transformations: `design-system/` is retained as noindexed internal QA specimen, every page remains noindexed and robots.txt still disallows indexing. After a future separately approved release PR sets a valid true manifest, the post-step prunes `design-system/` from the built artifact and generates a production robots.txt; the page meta robots tag is similarly conditional. The production artifact path is exercised only via synthetic temporary unit fixtures until release approval.
The manual release gate additionally requires nonempty, separately approved public contact and résumé configurations and an existing public PDF asset. This is a structural guard, not evidence that actual authorization or employer-policy review occurred. Do not change the release flag/approval, activate Pages, dispatch deploy, or purchase a domain without a separate PP-007B.2 owner decision. Static production metadata checks validate only the currently configured GitHub Pages base; if a domain changes, review the expected canonical URLs before release. See docs/PP_007B1_PRODUCTION_READINESS.md.

## PP-007B.1 final engineering QA (v0.14.0 candidate; publication still disabled)
The manual production workflow previously omitted the MVP inventory/privacy audit and production-preparation audit. The QA increment adds both and repeats the same critical CI tests including browser performance diagnostics. The MVP audit is explicitly dual-mode: prelaunch **requires** empty contact/résumé and noindex, whereas a future separately authorized production candidate **requires** exact published contact/resume configuration, matching PDF file, no fixture in output and production indexing. Fixture-only unit tests cover production transformations without flipping the real manifest. Failure of any gate aborts publication prior to Pages artifact upload.
No automated CI can substitute for an employer confidentiality decision, a specific résumé/public-link approval, physical-device and assistive-technology acceptance or independently verified GitHub Pages protections. Review docs/PP_007B1_FINAL_QA.md and release authorization requirements before modifying config/release.json.
