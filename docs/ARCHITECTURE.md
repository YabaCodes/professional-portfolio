# Architecture

Astro static output, Tailwind CSS v4 via official Vite plugin, TypeScript strict configuration, npm lockfile and Node 24 LTS. Exact dependencies and transitive resolution must be validated in CI. No backend, auth, runtime database or private data synchronization. Use base-aware links and asset URLs; GitHub project Pages base /professional-portfolio, future root custom domain requires separate config review.

src/pages: routes; src/layouts: page/article shells; src/components: shared UI; src/styles: tokens; src/assets: original optimized assets; src/content and src/content.config.ts: validated collections; src/lib/engineering: pure calculation logic; tests: unit/browser/accessibility.
Planned collections: case-studies, competencies, insights, demonstrations, publications, patents, credentials, career. Stable public IDs, slug, title, summary, evidence type, pillar, related competencies, public references, publication and revision dates. Validate referential integrity and evidence disclosure; approval register remains external. Do not populate with unapproved records.

CI checks build and type diagnostics at foundation; expanded unit/browser/axe tests in later increments. GitHub Pages deployment is separately authorized and manually triggered; no deployment workflow in this milestone. No React/Vue at foundation. Avoid dependencies without a documented need.

## Structured content and engineering — PP-004D
Eight JSON-backed collections under src/content, registered in src/content.config.ts. Shared strict Zod schemas and public record model are in src/lib/content. IDs are stable, category-prefixed; slugs are safe and unique per collection. Build-time catalog verifies allowed classifications, approval status, required public references, unique IDs, reserved routes, revision ordering and relationships. Competencies require supporting non-competency evidence. This is structural validation, never a substitute for external publication authorization or checking factual claims. The eight collections begin empty; test fixtures are synthetic and isolated from rendered content. Dynamic /work/[slug], /insights/[slug] and /insights/lab/[slug] use shared article layouts and render evidence labels and related records. JSON sections are escaped, plain-text content; richer authored article support may be added with review.
Engineering logic in src/lib/engineering is independent of Astro and UI. OEE accepts planned/operating minutes, ideal minutes per unit and integer counts, returns fractional A/P/Q/OEE and sequential loss fractions relative to planned time. OEE = ideal cycle time × good units / planned time; performance/quality are null when their denominators vanish. Zero planned time and inconsistent counts/times are rejected; above-100% theoretical performance requires input review, not silent clipping of materially inconsistent input. Numerical tolerance handles tiny floating error. No interactive lab UI until Phase 6. Unit tests use Node 24's native test runner; existing browser and contrast gates remain.

## Quality and release controls — PP-004E
CI runs on PRs and main pushes; clean install, type checks, native unit tests, design checks, static build, output audit, Chromium link/fragment/asset audit and responsive/axe regression. Initial coarse static budgets: 12 MiB total output, 150 KiB gzip generated JS, 100 KiB gzip generated CSS, 64 KiB gzip per HTML page. These are artifact budgets, not actual network transfer, LCP, INP or CLS measurements. Revisit via explicit review as content/tools grow. Output denylist and schema checks are supplementary safeguards, not complete secret scanning or content review. External reference URLs are counted, not contacted. The build remains noindex and robots-disallowed; not a privacy mechanism. See RELEASE_PROCESS for disabled manual publication workflow and outstanding launch controls.

## One-page résumé — PP-008
Supersedes the multi-route architecture above. The public site is one static route (/) plus the prelaunch-only /design-system/ specimen. Owner-approved wording lives in src/lib/portfolio.ts; identity and section anchors in src/lib/site.ts. Content collections are reduced to publications, patents, credentials and career; the catalog still validates IDs, approval status, references and relations at build time. Case-study, competency, insight and demonstration collections, src/lib/engineering and their tests are removed. The six phases use native `<details name="phase">` elements: keyboard operable, one open at a time in supporting browsers, all content readable without JavaScript. The only client script closes the mobile menu after a section is chosen. Motion is CSS-only progressive enhancement behind `prefers-reduced-motion: no-preference`: press feedback on buttons, a height transition on phase opening where `interpolate-size` and `::details-content` are supported, and a scroll-driven fade-in where `animation-timeline: view()` is supported; content is fully visible without it. Contact destinations come only from config/public-facing.json through the fail-closed gates (LinkedIn, email; résumé pending).
